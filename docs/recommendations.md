# Winner, Loser, Fatigue и рекомендации

Это отдельная аналитика без AI, queue или рекламных команд. GET
/api/recommendations читает PostgreSQL и возвращает четыре счётчика,
объекты, показатели, причины и дневные ряды. Категории можно фильтровать,
пагинация — 100 объектов. Счётчики рассчитаны для всех подходящих объектов,
а не только страницы. Источник и валюта не смешиваются.

## Условия

WINNER — одновременно Spend >= minimum_spend, Conversions >=
minimum_conversions, ROI >= target_roi и CPL <= target_cpl. ROI выражен
в процентах: прибыль / расходы × 100. CPL — расходы / лиды. Отсутствующий
показатель и деление на ноль не удовлетворяют условию.

STOP CANDIDATE — Spend >= loser_spend_multiplier × target_cpl и Leads = 0.
По умолчанию множитель 2. NULL leads не считается нулём. Это рекомендация
оператору, не автоматическая пауза.

CREATIVE FATIGUE — по умолчанию пять последовательных завершённых дней,
включая вчера. Сегодня исключён из тренда, так как день ещё продолжается.
CTR монотонно не растёт и снижается минимум на ctr_decline_percent;
CPC/Frequency/CPL монотонно не снижаются и растут минимум на свои пороги.
Процент изменения = (последнее − первое) / первое × 100. Нулевой baseline,
пропущенные дни, неизвестные метрики или недостаточный дневной объём
не подтверждают сигнал.

Пороги по умолчанию: Spend 50, Conversions 5, ROI 100%, CPL 10 в USD;
Fatigue: CTR −20%, CPC +20%, Frequency +10%, CPL +20%; минимум 100 показов
и 10 кликов в день. Это стартовые значения для настройки, не универсальные
нормативы. Они задаются через вкладку «Рекомендации».

Все детекторы возвращают проверки с фактическими значениями и порогами.
Один объект может совпасть с несколькими сигналами; категория выбирается
по приоритету Stop → Fatigue → Scale → Watch. Так fatigue не прячется за
положительным ROI. Watch означает отсутствие подтверждённого сигнала,
включая недостаток данных; конкретная причина отображается отдельно.

## Данные и сопоставимость

Уровень: campaign/adset/ad/creative; денежная валюта задана явно в settings.
Winner/Loser используют today/yesterday/last3/7/14/30, даты — по timezone
каждого кабинета. Требуются факты за каждый день выбранного окна;
пропущенные дни не достраиваются нулём. Ratios считают из сумм, без
усреднения процентов и предварительного округления пороговых значений.

Свежесть сегодня по умолчанию 30 минут, завершённых дней — 36 часов:
это соответствует периодическому перечитыванию истории. Для окон 14/30
может понадобиться отдельная свежая backfill-загрузка, поскольку стандартный
Smart Sync повторно читает семь дней. Устаревшее окно не даёт Winner/Loser.
Fatigue независимо проверяет свежесть всех завершённых дней и frequency.

На каждом дне используется один источник конверсий: FB либо полный
tracker. Смена источника между днями и неполный tracker запрещают
сравнение конверсионных метрик. Частично неизвестный итог остаётся NULL.
Для Fatigue дополнительно требуется одинаковый состав ad IDs каждый день.
Группировка использует текущие parent/creative links из БД; исторические
смены этих связей отдельно пока не архивируются. Fatigue показывает
математический сигнал по наблюдаемому ряду, не доказывает причину изменения.

## Frequency / Reach

В daily_metrics добавлены nullable reach и frequency. Старые строки после
миграции сохраняются с NULL, значения не выдумываются. В InsightSchema
есть optional field mappings. Синтетический фрагмент:
config/metricflow-frequency-fields.example.json. Он не является контрактом
MetricFlow: пути и дневную семантику нужно подтвердить на реальном API.
UI MetricFlow документирует [Reach и Frequency](https://metricflowit.click/docs),
но это само по себе не подтверждает конкретные поля ответа API.

Для одного объявления дневная frequency берётся из его строки либо
Impressions / Reach, если reach > 0. Для родительской сущности — из её
отдельной daily-записи с совпадающими date/currency/timezone/impressions
и актуальной observation. Родительский расход к ad totals не прибавляется.
Для группы из одного ad допустим fallback на его частоту. В группе из
нескольких ad reach не суммируется и частоты не усредняются: аудитории могут
пересекаться. Без корректной частоты Fatigue возвращает frequency_unavailable.

Основной sync настроен на ad-факты. Для Fatigue уровня adset/campaign с
несколькими объявлениями добавлена отдельная daily-загрузка /insights
по конфигу METRICFLOW_FREQUENCY_SCHEMA_FILE. В Compose это
config/metricflow-frequency-schema.json. Пример synthetic full schema:
config/metricflow-frequency-schema.example.json. Настраивать после проверки
живого parent-level ответа; это обычные полные daily rows, не среднее ad frequency.
Без config job не делает HTTP-запросов. При SYNC_ENABLED=true и валидном
config — каждый день в 04:27 по SYNC_TIMEZONE, 14 завершённых дней с
поправкой границ на timezones. Квота/пагинация/lease общие с Sync Engine.
В extra schema должны быть entity_level adset/campaign, impressions и
frequency или reach. Поля остальных доступных метрик тоже нужно явно
сопоставить: немаппированные значения остаются NULL. Winner/Loser продолжают
читать ad totals; parent spend к ним не прибавляется. Один extra config
синхронизирует один parent level; adset — уровень по умолчанию.

## Настройки и интерфейс

recommendation_settings хранит один JSON config и revision на workspace.
GET читает defaults, не записывая их. PUT /api/recommendations/settings
доступен operator/admin через серверную identity. CAS revision не даёт
перетереть чужое изменение. Цели, число дней, объём и свежесть валидируются.

Вкладка показывает Scale/Watch/Stop/Fatigue, фильтры категорий, причины,
проверки и четыре графика с дневной таблицей. Числа всегда из БД. Пустая
БД даёт нулевые счётчики, без демонстрационных победителей/расходов.
Если оператор решит выполнить действие, используется существующий
Action Engine/Rule Engine; детекторы сами ничего туда не отправляют.
