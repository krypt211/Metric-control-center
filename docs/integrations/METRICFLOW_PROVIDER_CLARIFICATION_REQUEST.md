## 1. Соответствие ID

Для level=ad entity_id в WRITE path равен InsightRow.ad_id, полю id из другого
READ endpoint или внутреннему ID MetricFlow? Укажите точное соответствие
READ endpoint/JSON field -> WRITE entity_id и способ проверить принадлежность
объекта ad_account_id/campaign_id/adset_id в том же owner/team context.
Достаточно примера с вымышленными согласованными ID.

## 2. Асинхронный ответ

В description PAUSE/ENABLE обещан HTTP 202 + job_id, но formal responses
перечисляют только 200 и 422. Каковы точные headers/body/schema 202?
Когда HTTP 200 означает выполненное изменение, а когда только принятие команды?
При каких условиях job_id может быть null?

## 3. Права конкретного объекта

Подтвердите entities:write и дополнительные asset/profile/team/acting-as права
для PAUSE/ENABLE одного AD и GET его job. Как проверить effective management
permission без пробного WRITE? Если такого non-mutating endpoint нет, укажите
это и опишите другой авторитетный способ проверки доступа.
Какие состояния подписки/access_state разрешают эти операции?

## 4. Ошибки и неоднозначный результат

Нужны примеры ошибок 400/401/402/403/404/408/422/429/5xx, error codes, Retry-After
и условия, при которых изменение могло уже примениться несмотря на ошибку.
Для single-AD job уточните partial/failed/expired и per-entity results:
может ли одно из этих состояний означать уже изменённый статус на Facebook?
Какие polling intervals, квоты и retention применяются к GET /jobs/{job_id}?

## 5. Потерянный job_id и idempotency

Поддерживается ли Idempotency-Key/client operation ID именно для PAUSE/ENABLE?
Если да: заголовок/поле, scope, срок хранения, повторный и конфликтующий ответы.
Если POST завершился timeout до получения job_id, каким документированным GET
найти исходную операцию без повторного POST? Если lookup отсутствует,
подтвердите отсутствие. Наша сторона не повторяет неопределённую команду и
сохраняет UNKNOWN до выяснения результата.

## 6. Авторитетный readback

Что означают status/effective_status в insights и ads READ: configured_status
объекта и фактический статус с учётом родителей или другие значения?
Какие GET/поля/timestamps доказывают изменение конкретного AD после job success?
GET возвращает кеш MetricFlow или запрашивает Facebook? Есть ли гарантированный
срок обновления и read-your-writes? ApiMeta.data_updated_at относится к источнику,
кабинету, периоду или конкретному объекту? Нужны также статусы родителей.

## 7. Attribution исторических insights

Для leads/purchases/conversions в GET /insights уточните attribution windows,
action_report_time, timezone календарного дня и точную семантику leads.
Применяется fixed или unified/adset attribution? Где прочитать фактически
применённую настройку: точный существующий GET, JSON paths, types и пример?
Если READ metadata нет, опишите фиксированный контракт с версией, датой введения
и областью действия. Может ли семантика различаться по AD/account/дате/импорту?
Как меняются прошлые дни при смене настроек и поступлении поздних конверсий?

Найденный AdsetSpec.attribution_spec относится к input создания adset;
он не доказывает настройку конкретных исторических строк insights.
Пожалуйста, явно укажите и неподдерживаемые возможности. Мы не будем
придумывать поля, ID, retry или attribution. Реальные действия потребуют
отдельного разрешения пользователя после технической приёмки.
