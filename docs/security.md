# Разделение доступа

Два отдельных ключа с минимальными правами:

| Ключ | Scopes | Получатели |
|---|---|---|
| READ | analytics:read, ad_accounts:read, campaigns:read, rules:read, bundles:read | ingestion worker |
| WRITE | campaigns:write | action worker |

Настройка scopes выполняется в MetricFlow. GET-only клиент уменьшает
риск случайной записи, но не исправляет ошибочно выданные права самого ключа.

Секреты читаются из файлов: METRICFLOW_READ_KEY_FILE и
METRICFLOW_WRITE_KEY_FILE. Значения не входят в .env.example, Docker image,
Git, frontend или сообщения об ошибках. Ответы API не включаются в ошибки:
они могут содержать чувствительные данные.

Compose выдаёт каждому сервису только указанные секреты через /run/secrets.
Файлы .secrets должны быть доступны только владельцу на хосте; Compose
не является зашифрованным хранилищем секретов. В production можно заменить
файлы секретами инфраструктуры, сохранив контракт *_KEY_FILE.

HTTP redirects не выполняются, чтобы не переслать ключ на другой адрес.
Системные HTTP-прокси не подхватываются автоматически.
Не включать отладочное логирование HTTP-заголовков.

Реализованы policy, аудит, проверка актуальности, ограничения суммы/процента,
идемпотентность и одна незавершённая команда на сущность. Внешний 2xx не
считается подтверждением конечного состояния: команда остаётся verifying.
После сбоя worker зарегистрированная попытка не отправляется повторно.
При неопределённом результате сущность блокируется до сверки.

В локальной версии операторский токен хранится только в backend/Next.js,
не в браузере. Он определяет настроенную на сервере запись User; клиент
не может подставить инициатора в JSON. User должен иметь role operator/admin
и принадлежать рабочему пространству. Это локальный режим одного оператора,
не полноценная система командных сессий для публичного размещения.

Сейчас Redis общий для worker. Это не граница защиты от
скомпрометированного backend: для серверной изоляции
нужны ACL/отдельный broker и отдельные DB grants. Task не принимает произвольные
рекламные payloads: worker забирает принятую и проверенную заявку из БД.
Публичный доступ к дашборду добавляется после пользовательских сессий.

Rule Engine и Batch API получают только доступ к БД и Action Engine,
не MetricFlow WRITE. DRY_RUN не создаёт ActionRequest. ACTIVE передаёт
команду той же policy, затем action worker повторяет проверки. OFF/смена
revision/устаревшая статистика отменяют ещё не отправленную rule-команду.
AI передаёт предложения в этот же контур с серверной identity и причиной;
WRITE остаётся у action worker. Inference worker получает только OpenAI key
и БД; Telegram — только bot token и БД. Режимы OFF/READ_ONLY/RECOMMEND не создают рекламных
заявок. Approval сохраняется атомарно с ActionRequests; worker проверяет наличие
durable approval, policy revision, expiry, evidence fingerprint и дневной лимит.
LLM output не определяет права, инициатора или provider endpoint.
Telegram callback проверяет явную private-chat binding, владельца и message ID.
По умолчанию AI/Telegram/Autopilot выключены. Подробности: [ai-copilot.md](ai-copilot.md).

Общий Emergency Stop хранится в БД и повторно проверяется перед POST.
Поколение остановки не позволяет восстановить старые предложения после resume.
Уже отправленный запрос отозвать нельзя; ingestion и ручные команды продолжают работать.
Все рекламные команды из чата требуют CONFIRM, даже в Autopilot.
Модель не может одобрить план, возобновить автоматику или менять инструкции/права.
Профили GEO/offer имеют optimistic revision и не расширяют общую policy.
Tool trace и история чата доступны только своему оператору через authenticated API.
